# Shopping Copilot 项目创新点

## 1. 创新总览

Shopping Copilot 的创新不在于“接入了某一个大模型”，而在于把购物搜索设计成一个会随着对话变化的决策系统。

它持续回答三个问题：

1. 用户现在是在购买，还是在探索？
2. 当前有效条件下，应该如何找和排商品？
3. 如果还不能直接推荐，下一轮最值得问什么？

这三点正好对应比赛要求的意图路由、多轮场景演化和效率评测。

## 2. 创新点一：Buying / Browsing 双轨体验

多数搜索系统把所有请求都当成同一种关键词检索。Shopping Copilot 先判断用户任务类型，再选择不同的产品策略：

- Buying 走精确路径，优先预算、尺码、品类、颜色等硬条件；
- Browsing 走探索路径，保留场景和风格语义，结果更加多样。

**用户价值：**明确购买时不会被大量无关商品干扰；还在探索时也不会因为条件不足而过早得到狭窄结果。

**Demo 证据：**用“黑色、100 美元以内跑鞋”和“夏季婚礼穿搭”两个例子对比展示。

## 3. 创新点二：槽位级会话记忆，而不是简单拼接历史

用户的偏好被拆成可更新的需求槽位，并区分硬约束、软偏好和上下文。系统不会把所有历史句子机械地拼在一起，而是维护“当前仍然有效的需求状态”。

当用户说“其实任何品牌都可以”时，系统只移除品牌限制；预算、品类和颜色仍然有效。

**用户价值：**对话更符合人的记忆和改口习惯，避免旧条件持续污染结果。

**比赛价值：**直接改善 Intent Override 场景，也能降低不必要的对话轮次。

## 4. 创新点三：澄清问题也是搜索动作的一部分

系统不是“要么问问题、要么给结果”的二选一流程。当前候选仍然保留，Agent 根据候选范围判断是否需要澄清，并尽量在提问的同时让用户看到当前方向。

问题选择关注的是“这个属性能不能真正区分候选”，而不是简单按固定顺序逐项询问。

**用户价值：**减少无产出的追问，让每一轮都推动购物决策前进。

**Demo 证据：**从“I want some shoes”开始，展示系统询问用途或品类，而不是泛泛地说“请提供更多信息”。

## 5. 创新点四：把排序质量当作核心产品问题

比赛数据显示，正确商品通常已经进入候选池，真正困难的是它没有排在足够靠前的位置。因此项目优化重点不是盲目扩大召回，而是提升 rank1 质量。

当前排序结合：

- 属性检索中的 reciprocal rank 信号；
- 标题、品类和特征匹配；
- 硬条件完整度；
- 当前有效的会话证据。

**用户价值：**用户更快看到真正相关的商品，而不是在 Top 10 中自行翻找。

## 6. 创新点五：结构化状态与确定性降级并存

可选模型不可用、输出不完整或索引出现问题时，Agent 仍可通过规则解析和本地排序完成响应。系统把模型当作增强能力，而不是唯一依赖。

**用户价值：**更稳定的响应和更容易解释的失败处理。

**比赛价值：**符合 offline-first 的限制，评测不依赖临时 API、网络或额外付费额度。

## 7. 创新点六：用统一指标连接产品体验和工程结果

项目没有只展示“看起来不错的几条推荐”，而是用官方评测器持续验证：

- 是否找到正确商品（Hit Rate@10）；
- 是否排得足够靠前（MRR）；
- 是否问得足够少（MTTC）；
- 综合表现是否提升（TechnicalScore）；
- 响应是否满足延迟预算（p95）。

当前公开集结果：

| 指标 | 当前结果 |
|---|---:|
| Hit Rate@10 | 0.9600 |
| MRR | 0.606629 |
| MTTC | 2.585 |
| TechnicalScore | 0.830289 |
| p95 | 68.675 ms |

这让 demo 可以同时回答“产品为什么这样做”和“效果如何证明”。

## 8. 与普通聊天式推荐的区别

| 普通聊天推荐 | Shopping Copilot |
|---|---|
| 主要生成描述或建议 | 维护可更新的购物状态 |
| 所有请求使用相似搜索方式 | 按 Buying / Browsing 选择路径 |
| 历史消息容易越积越乱 | 用户改口时只更新受影响槽位 |
| 追问和推荐通常分开 | 追问服务于候选收敛，并保留结果方向 |
| 依赖模型自由发挥 | 目录只读、结果可校验、失败可降级 |
| 依赖个别案例展示 | 使用统一公开集和自建集指标验证 |

## 9. Demo 讲解时的表达方式

推荐使用下面的表达：

> 我们把购物从一次搜索变成一个可修正的决策过程。Agent 先识别用户是在买还是在看，再维护当前有效偏好，并用最有价值的问题推动结果收敛。它的创新是把对话理解、检索排序和效率放进同一个闭环。

避免使用下面的表达：

- “我们只是把 BM25 换成了一个更大的模型”；
- “模型自己理解了所有内容”；
- “这个样本刚好被我们调出来了”；
- “只要多问几轮就一定能找到”。

## 10. 创新边界与诚实说明

这是一个 hackathon 原型，不是完整电商平台。当前没有支付、库存、订单和真实用户账号，也没有声称解决所有商品类别或多模态输入问题。

这种边界说明反而能体现项目的可信度：我们在比赛规定的数据、接口和 10 轮限制内，完成了可复现、可评测、可演示的对话式检索成果。
