# Shopping Copilot 多轮意图与状态路由实施方案

## 1. 文档目标

本文基于当前 Shopping Copilot 代码、公开评测器和 Stage 3 基线，给出一套适用于不超过 10 轮对话的实施方案。实施顺序固定为：

```text
状态语义补全和事件规则
  -> 路由真正驱动检索与 Dialogue Policy
  -> NLI shadow 验证
  -> 校准后受控启用
```

这个顺序解决两个核心问题：

1. 当前 Buying、Browsing、Unknown 在 BM25-only 配置下几乎没有排序差异，只替换意图分类器难以转化为端到端收益。
2. 多轮准确率不仅取决于本轮意图，还取决于上一轮问了什么、用户是否回答或拒答、旧槽位是否仍有效，以及改口事件作用于哪些状态。

最终目标不是追求孤立的意图分类准确率，而是提升四类场景的 `HitRate@10`、`MRR` 和 `MTTC`，同时保证状态稳定、回退确定、模型故障不影响基本服务。

## 2. 当前基线与有效性判断

官方综合目标为：

```text
TechnicalScore = 0.50 * HitRate@10 + 0.30 * MRR + 0.20 * Efficiency
Efficiency = clip((11 - MTTC) / 10, 0, 1)
```

当前确定性 Stage 3 基线来自 `.runtime/phase3-public-results.json`：

| 场景 | 样本数 | Hit@10 | MRR | MTTC |
|---|---:|---:|---:|---:|
| Buying | 80 | 0.3125 | 0.188676 | 8.0125 |
| Browsing | 80 | 0.3500 | 0.237862 | 8.9000 |
| Intent Override | 30 | 0.2000 | 0.177778 | 9.6333 |
| Boundary | 10 | 0.3000 | 0.300000 | 9.5000 |
| Overall | 200 | 0.3100 | 0.212282 | 8.6850 |

对公开评测器首轮消息使用当前 `RuleIntentRouter` 诊断，结果为：

| 场景 | 当前首轮路由结果 | 结论 |
|---|---|---|
| Buying | 31 Buying / 49 Unknown | 类别词表覆盖不足，但 Unknown 当前仍走近似 Buying 的默认检索 |
| Browsing | 45 Browsing / 35 Buying | `still exploring` 可能被 `looking for + 商品词` 压过 |
| Intent Override | 15 Buying / 15 Unknown | 改口后的事件和槽位处理比首轮分类更关键 |
| Boundary | 5 Browsing / 5 Buying | 初始分轨和通用 no-preference 事件均需加强 |

当前命中轮次还显示：

- Buying 的 25 个命中中有 21 个发生在首轮，剩余失败主要不是多轮意图分类问题。
- Browsing 的命中主要集中在第 5-6 轮，追问选择和槽位披露决定收益。
- Intent Override 的 6 个命中全部发生在改口后的第 4-5 轮，状态替换和查询重建是核心。
- Boundary 首次拒绝偏好没有信息增益，需要避免把拒答当成新偏好或重复追问。

因此，本方案不把 NLI 模型作为第一阶段。先建立正确的状态语义和可观察的路由差异，才能判断模型是否带来真实收益。

## 3. 当前链路与主要缺口

当前链路为：

```text
starter.Agent.respond
  -> ShoppingAgentCore.respond
  -> SessionStateStore.begin_turn
  -> FallbackStructuredParser.parse
       -> DeepSeekStructuredParser（可选，默认关闭）
       -> RuleConstraintExtractor.parse
            -> RuleIntentRouter.route
            -> 规则槽位、否定、clear、override 抽取
  -> Core 写入 state.intent
  -> OverrideResolver.apply
  -> HybridRetriever.retrieve
  -> ClarificationPolicy.decide
  -> response / trace
```

### 3.1 状态缺少对话语义

当前 `SessionState` 只有用户消息 `history`、无序且永久累积的 `asked_slots`、没有具体槽位的 `last_action`、槽位值和简单意图字段。这不足以判断用户是在回答上一轮、拒绝回答、添加偏好，还是切换轨道。

### 3.2 事件检测不完整

当前规则只覆盖部分 `actually/instead`、brand clear 和颜色否定，尚未形成独立且带作用域的事件结果，不能稳定覆盖：

```text
I don't have a preference for color.
Ignore my earlier preference.
Keep the budget, but change the brand.
Anything except red.
No longer looking for boots; show me sneakers.
```

### 3.3 路由没有充分改变下游

当前路由主要影响 dense query、dense subset 和 lexical/dense 权重。dense 关闭时只剩 lexical 来源，RRF 归一化后 Buying/Browsing 排序基本相同。`ClarificationPolicy` 也统一使用：

```text
category -> price_max -> size -> color -> brand -> material
```

因此分类正确不等于推荐和下一轮输入会改变。

### 3.4 多轮状态可能残留

`SlotValue.active_weight()` 没有参与过滤、查询或排名，`OverrideResolver.decay()` 也没有在主链路调用。带 TTL 的软槽位实际上不会失效。`asked_slots` 同时承担“问过”和“不再问”的职责，也没有在意图切换后重新评估。

## 4. 目标架构

```text
begin_turn
  -> RuleConstraintExtractor：高精度槽位
  -> RuleEventDetector：override/clear/negation/no_preference/switch
  -> RuleIntentRouter：规则意图证据
  -> IntentClassifier：off/shadow/active
  -> IntentResolver：融合规则、模型、事件和稳定状态
  -> TurnStateReducer：原子更新状态
  -> intent-aware query/retrieval/policy
  -> response / structured trace
```

建议模块：

```text
src/nlu/intent/
  schema.py
  resolver.py
  nli.py
  hypotheses.py
src/nlu/events.py
src/state/reducer.py
```

`continue` 是解析决策，不是可写入状态的第四条检索轨道。稳定意图仍只允许 `buying/browsing/unknown`。

## 5. Phase A：状态语义补全和事件规则

### 5.1 状态模型

```python
@dataclass(frozen=True)
class AskedSlotState:
    slot: str
    turn: int
    status: Literal["asked", "answered", "declined"]
    route: Literal["buying", "browsing", "unknown"]

@dataclass(frozen=True)
class IntentState:
    label: Literal["buying", "browsing", "unknown"]
    confidence: float
    source: str
    stable_since_turn: int
    last_switch_turn: int | None = None
    switch_reason: str | None = None
```

`SessionState` 增加：

```python
intent_state: IntentState
last_asked_slot: str | None
slot_answers: dict[str, AskedSlotState]
last_user_message: str
previous_user_message: str | None
```

兼容期保留现有 `intent` 和 `intent_confidence` 属性，由 `intent_state` 派生。

### 5.2 回答状态迁移

| 当前情况 | 用户输入 | 状态更新 |
|---|---|---|
| 上轮询问 color | `black` | color=black，answered，沿用稳定意图 |
| 上轮询问 brand | `any brand is fine` | 清除 brand 软偏好，declined |
| 上轮询问 size | 无法解析的泛化回复 | 保持 asked，不伪造 answered |
| 已有 color=black | `actually white instead` | clear 后 set white，记录 override |
| 已有 Buying | `I'm just exploring options now` | 显式切换到 Browsing |

`last_asked_slot` 只在成功返回澄清问题时更新。下一轮根据事件和槽位结果转为 `answered` 或 `declined`。

### 5.3 统一事件类型

```python
@dataclass(frozen=True)
class TurnEvent:
    kind: Literal[
        "override", "clear", "negation", "no_preference", "intent_switch"
    ]
    slots: frozenset[str]
    confidence: float
    explicit: bool
    evidence: tuple[str, ...]
```

事件和 Buying/Browsing 独立。一句话可以同时产生 `intent=buying`、`event=override(color)` 和 `slot_update=color:white`。

### 5.4 状态修改顺序和边界

```text
明确 clear
  -> 同槽位 override 的旧值移除
  -> negation 写入 exclusions
  -> 新 slot_updates
  -> 冲突检测
  -> intent 状态提交
```

规则约束：

1. `no preference for X` 只清理 X 的软偏好，不清理无关硬约束。
2. 无明确槽位的 `ignore earlier preference` 不允许清空全部状态；只处理最近可覆盖软槽位，或进入澄清。
3. `instead/no longer` 同时出现旧类别和新类别时允许明确类别切换。
4. 预算、尺码和显式排除不得由低置信度模型事件清除。
5. NLI 永远不能直接产生 destructive state mutation。

### 5.5 软槽位有效性

- hard 槽位持续有效，直到明确 clear/override；
- user-confirmed soft 槽位默认持续有效；
- model/context soft 槽位按 TTL 计算权重；
- `active_weight == 0` 的槽位不得进入 query/filter/ranking；
- 历史保留原值，生效视图只返回 active slots。

统一提供：

```python
state.active_slots(turn)
state.active_constraints(turn)
```

下游禁止直接遍历所有 `state.slots` 构建查询。

### 5.6 Phase A 验收

- 短回答能绑定最后一次询问槽位。
- `asked/answered/declined` 均有测试。
- no-preference 后不重复询问相同属性。
- 同槽位 override 按 `clear -> set` 执行。
- 模糊 clear 不会删除全部状态。
- 过期软槽位不再进入有效 query/filter。
- 第 10 轮状态可审计，session 无泄漏。

## 6. Phase B：让路由真正驱动检索与 Policy

Phase B 先使用增强后的规则路由，不启用 NLI，以建立模型无关业务基线。

### 6.1 统一路由结果

```python
@dataclass(frozen=True)
class ResolvedIntent:
    label: Literal["buying", "browsing", "unknown"]
    confidence: float
    source: str
    switched: bool
    reason: str
```

融合顺序：

```text
明确 intent_switch
  -> 强购买/浏览规则
  -> 上轮问题的有效回答：continue
  -> 已有稳定意图
  -> unknown
```

### 6.2 Buying 检索

- 使用 `active_constraints()` 重建 query，不拼接无限历史；
- 预算、尺码、明确排除和确认类别作为硬约束；
- lexical 权重高于 dense；
- dense 仅在 hard-filter subset 中补召回；
- clear 的偏好不能被旧 query 文本重新带回；
- 空集放宽禁止移除预算和显式排除。

### 6.3 Browsing 检索

- dense 使用当前场景、用途、风格和最近一轮有效表达；
- 不使用过硬 category subset，只保留预算和明确排除等边界；
- 对 category、brand 或高度重复标题做轻量 diversity rerank；
- `occasion/use_case/style` 作为软语义字段进入 dense query；
- dense 不可用时，BM25 query 仍保留场景词。

需要同步扩展状态和 query schema，使 `occasion/style/use_case` 真正生效。

### 6.4 Unknown 和 Override

Unknown：已有稳定意图时沿用；首轮 unknown 使用均衡融合；dense 关闭时明确记录其与 Buying 尚无排序差异；缺少 category/use_case 时优先询问高信息量问题。

Override：原子更新槽位，从 active state 重建 query，当前轮立即重检索，不复用旧 query；未抽出新槽位时以本轮原文做语义查询并追问最相关属性。当前代码每轮已覆盖候选池，无需额外设计候选缓存清空机制。

### 6.5 意图感知 Policy

Buying 优先级：

```text
category -> budget -> size -> brand/color/material
```

Browsing 优先级：

```text
use_case/occasion -> style -> category -> budget
```

Boundary：`declined` 槽位不再询问；从剩余属性选择信息增益最高者；没有高价值问题则推荐；no-preference 不改变路由。

轨道切换时保留仍相关的已回答槽位和 declined 状态；与旧类别绑定的 style/use_case 可失效；Policy 按新 route 重新计算可问槽位。

### 6.6 澄清停止条件

除 turn 和候选数外，增加：

- Top 10 已稳定；
- Top1-Top2 margin 达到校准阈值；
- 没有高信息量未回答槽位；
- 连续澄清没有使候选集收缩；
- 当前轮已是第 8 轮或之后。

每轮响应都会返回候选，Policy 的主要作用是决定评测器下一轮披露什么信息。

### 6.7 Phase B 消融

| 版本 | 状态/事件 | 路由检索 | 路由 Policy | 用途 |
|---|---|---|---|---|
| B0 | 当前 | 当前 | 当前 | Stage 3 基线 |
| B1 | 新 | 当前 | 当前 | 测状态正确性 |
| B2 | 新 | 新 | 当前 | 测检索收益 |
| B3 | 新 | 新 | 新 | 无 NLI 新基线 |

只有 B3 稳定高于 B0 才进入 NLI 验证，否则先修复状态、查询或 Policy。

## 7. Phase C：NLI Shadow 验证

### 7.1 模型职责

候选模型为 `cross-encoder/nli-deberta-v3-xsmall`。模型只输出 `buying/browsing/continue/unknown`；`continue` 由 Resolver 转换为已有稳定意图，绝不写入状态。

`override/clear/negation/no_preference/destructive intent switch` 继续由规则处理。

### 7.2 输入和 Hypothesis

最多使用一轮上下文：

```text
Previous stable intent: browsing.
The assistant asked about color.
Known active preferences: category and budget.
The customer now says: "black".
```

只传 stable intent、`last_asked_slot`、active slot names、当前消息和必要时上一轮用户消息。不传目录、候选、完整历史或评测标签。

```text
buying: The customer has a specific purchase goal and wants products satisfying concrete requirements.
browsing: The customer is exploring ideas, styles, occasions, or options without a fixed target.
continue: The customer is answering the previous shopping question or adding a preference without changing shopping mode.
```

`continue` 与其他标签可能重叠。若竞争式三标签 softmax 导致抢占，应改成两阶段：先判断 continue/switch，再判断 buying/browsing。

### 7.3 Shadow Mode

- 规则和状态 Resolver 继续控制行为；
- NLI 每轮推理但不修改 intent、query、filter 或 Policy；
- trace 同时记录规则、模型和最终规则路由；
- 模型缺失、checksum 错误或推理异常只记录 fallback。

新增 trace：

```text
rule_intent / rule_confidence
model_intent / model_confidence / model_margin
stable_intent_before / resolved_intent
intent_switched / switch_reason
last_asked_slot / slot_answer_status
detected_events
intent_model_mode / intent_fallback_reason / intent_latency_ms
```

不得记录原始 embedding、模型绝对路径、secret、私有标签或无限长度原文。

### 7.4 验证集和门槛

| 类型 | 建议数量 | 覆盖重点 |
|---|---:|---|
| Buying | 150-200 | 显式购买、隐式约束、长尾类别 |
| Browsing | 150-200 | 场景、灵感、商品词与 exploring 冲突 |
| Continue | 150-200 | 短回答和无新增偏好回复 |
| Switch | 100-150 | Buying/Browsing 双向切换 |
| Confusion | 150-200 | `show options`、`need ideas` 等 |
| Events | 150-200 | 独立评估事件规则 |

按模板家族隔离校准集和最终测试集。进入 active 前要求：intent macro-F1 `>= 0.90`、Buying -> Browsing 误判 `< 5%`、Continue recall `>= 0.90`、明确 switch recall `>= 0.90`、各事件 recall `>= 0.90`，且 fallback 行为与 B3 一致。

## 8. Phase D：校准后受控启用

### 8.1 Resolver

```python
def resolve_intent(rule, model, state, events):
    if events.has_explicit_intent_switch:
        return events.switch_target
    if rule.has_strong_explicit_signal:
        return rule.label
    if model.label == "continue" and state.has_stable_intent:
        return state.stable_intent
    if state.has_stable_intent:
        if model.confidence >= switch_confidence and model.margin >= switch_margin:
            return model.label
        return state.stable_intent
    if model.confidence >= initial_confidence and model.margin >= initial_margin:
        return model.label
    return "unknown"
```

阈值只能从固定验证集校准，不能逐条针对 public sessions 调优。

### 8.2 启用模式

```text
off     -> 不加载模型，使用 B3
shadow  -> 推理并记录，不影响行为
active  -> 通过 Resolver 影响路由
```

默认发布为 `off` 或 `shadow`，只有端到端 D 版本通过验收才切换为 `active`。

### 8.3 Artifact 与回退

运行时禁止下载、训练或转换。manifest 至少包含：

```json
{
  "model_id": "cross-encoder/nli-deberta-v3-xsmall",
  "runtime": "onnxruntime-int8",
  "artifact_variant": "quint8-avx2",
  "labels": ["contradiction", "entailment", "neutral"],
  "hypothesis_version": "shopping-intent-v1",
  "resolver_version": "intent-resolver-v1",
  "model_sha256": "...",
  "tokenizer_sha256": "..."
}
```

启动时校验文件、checksum、ONNX I/O、label mapping、execution provider，并执行一次健康检查。任一失败立即回退 B3，不允许导致 Agent 初始化失败。

### 8.4 端到端消融

| 版本 | 状态/事件 | 检索/Policy | NLI | 目的 |
|---|---|---|---|---|
| A | 当前 | 当前 | off | 原始基线 |
| B | 新 | 新 | off | 规则业务基线 B3 |
| C | 新 | 新 | shadow | 测模型与延迟，不改行为 |
| D | 新 | 新 | active | 测完整收益 |
| E | 新 | 新 | active 但禁用模型切轨 | 区分 Continue 与切轨收益 |

最终必须比较 D 相对 B，不能只比较 D 相对旧 A。

## 9. 测试矩阵

单元测试覆盖事件组合、Resolver 防抖、Reducer 原子更新、active slots、query 清理和三条路由的 Policy。

多轮组合至少覆盖：

```text
Browsing -> 短回答 -> 短回答 -> Buying switch
Buying -> no preference -> 继续 Buying
Buying -> color override -> budget 保留
Browsing -> category switch -> 旧 style 失效
Unknown -> 明确约束 -> Buying
模型连续低置信 -> 稳定意图不变
模型异常 -> 全程规则 fallback
```

回归要求：session 隔离；turn 只能从 1 到 10 单调增长；每轮返回合法去重 Top 10；第 10 轮不依赖继续回答；trace 无 secret；dense/NLI 不可用时仍确定运行。

## 10. 验收标准

Phase B：B3 Overall TechnicalScore 高于 `0.264985`；Override Hit@10 高于 `0.20`；Buying Hit@10 不低于 `0.3125`；Browsing Hit@10 不低于 `0.35` 或 MRR 明确提升且总分上升；Boundary 不因重复澄清退化。

NLI Active：D 必须高于 B；四场景无不可接受退化；事件指标不因 NLI 下降；`respond` p95 增幅在预算内；关闭或故障后恢复 B 的确定性行为。

若 D 只提高离线 intent accuracy，但端到端不高于 B，则保持 `shadow` 或 `off`。

## 11. 实施顺序

### Phase A：状态和事件

1. 增加 `last_asked_slot` 和回答状态。
2. 拆分 constraint、event 和 intent 规则。
3. 新增唯一状态修改入口 `TurnStateReducer`。
4. 实现 active slot 视图和真实软槽位失效。
5. 补齐 Override、Boundary 和多轮测试。

### Phase B：下游路由

1. 实现三条 route query builder。
2. 打通 `occasion/style/use_case`。
3. 分离 retrieval subset 和融合策略。
4. 实现 intent-aware Policy 与停止条件。
5. 运行 B0-B3 消融并冻结 B3。

### Phase C：Shadow

1. 准备本地只读 artifact 和 manifest。
2. 实现 premise、hypothesis 和 batch 推理。
3. 增加 shadow trace。
4. 验证并冻结 hypothesis。
5. 检查 fallback、延迟和内存。

### Phase D：Active

1. 校准 confidence 和 margin。
2. 通过 Resolver 受控启用。
3. 运行 B/C/D/E 和四场景报告。
4. 只有 D 明确高于 B 时默认 active。

## 12. 风险与控制

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 下游仍读旧状态字段 | 新语义不生效 | 统一 reducer 和 active state API |
| asked/declined 混用 | 重复或漏问 | 显式回答状态机 |
| 模糊 clear 过度删除 | 丢失硬约束 | 事件作用域和 destructive guard |
| 路由正确但 BM25 不变 | 分数不涨 | Phase B 先建立真实下游差异 |
| Browsing 过度放宽 | 噪声增加 | 保留预算/exclusion，轻量多样性 |
| Continue 抢占切换 | 意图无法更新 | 强事件优先，必要时两阶段分类 |
| 针对 public set 调参 | 私有集退化 | 模板隔离并冻结测试集 |
| Artifact 不兼容 | 模型不可用 | 健康检查和 B3 fallback |
| NLI 延迟过高 | p95 上升 | 单 batch、短上下文、常驻、可关闭 |

## 13. 最终建议

```text
补齐 last_asked_slot、回答状态和 active slots
  -> 建立高精度事件规则与原子 reducer
  -> 实现 Buying/Browsing/Unknown 的检索与 Policy 差异
  -> 冻结无模型 B3 基线
  -> NLI shadow 验证语义增益和延迟
  -> 校准 Resolver
  -> 只有端到端 D > B 时启用 active
```

状态和事件保证正确性，检索和 Policy 产生业务影响，NLI 只负责规则难以覆盖的语义泛化。任何阶段都保留确定性规则回退，模型不可用时不会破坏 Agent 基本能力。
